- Software Architect

- UI/UX Designer

Il tuo incarico è progettare, sviluppare, verificare e consegnare **WORLDWEAVE 1.0**, una piattaforma web completa per la creazione, organizzazione e collaborazione nella costruzione di universi narrativi fantasy.

Non devi realizzare un prototipo, una demo, una landing page o un MVP.

Devi realizzare un'applicazione software completa, utilizzabile e distribuibile autonomamente.

# 2. OBIETTIVO DEL PRODOTTO

WORLDWEAVE è un ambiente di worldbuilding fantasy che consente agli utenti di creare e gestire universi narrativi complessi.

La piattaforma deve integrare:

- gestione degli universi;
- gestione di società, popoli e culture;
- enciclopedia narrativa strutturata;
- documentazione e cronache;
- relazioni tra entità;
- mappe interattive;
- cronologie storiche;
- collaborazione multiutente;
- gestione di ruoli e permessi;
- importazione ed esportazione dei contenuti.

L'esperienza deve essere coerente, elegante, immersiva e funzionale.

L'interfaccia deve comunicare l'atmosfera di un archivio fantasy editoriale, senza compromettere leggibilità, accessibilità e usabilità.

Non creare un'interfaccia generica da dashboard amministrativa.

# 3. ARCHITETTURA OBBLIGATORIA

Realizza un modular monolith. Non utilizzare microservizi.

## Frontend

- React
- TypeScript con strict: true
- Vite
- Tailwind CSS
- shadcn/ui personalizzato
- TanStack Query
- React Router
- React Hook Form
- Zod
- TipTap
- Yjs per la collaborazione sui documenti
- Cytoscape.js per i grafi
- Leaflet per le mappe, con coordinate normalizzate e CRS.Simple quando richiesto
- Vitest
- React Testing Library
- Playwright

## Backend

- Python
- FastAPI
- Pydantic
- SQLAlchemy 2.x
- Alembic
- PostgreSQL
- WebSocket
- pytest

## Infrastruttura

- Docker Compose
- PostgreSQL
- Redis opzionale, esclusivamente per cache o coordinamento effimero
- Filesystem locale
- Architettura predisposta per un futuro adapter S3-compatible
- Caddy o Nginx per il reverse proxy e TLS
- SMTP opzionale, con possibilità di copiare un link di invito quando SMTP non è configurato.

Non introdurre servizi SaaS obbligatori.

La piattaforma deve poter essere installata e gestita autonomamente.

## Regole architetturali

- PostgreSQL è la fonte autorevole dei dati strutturati.
- Markdown è un formato di importazione ed esportazione, non un archivio canonico parallelo.
- Gli identificativi devono essere UUID opachi.
- Tutte le date e gli orari devono essere gestiti in UTC.
- Le API devono utilizzare il prefisso /api/v1.
- JSON in snake_case.
- Paginazione coerente.
- Errori API con schema stabile.
- Nessuno stack trace nelle risposte al client.
- Le righe appartenenti a un universo devono essere correttamente isolate tramite universe_id.
- Utilizzare vincoli e transazioni database per garantire l'integrità.

# 5. AUTENTICAZIONE E SICUREZZA

Implementa un sistema reale di autenticazione e gestione delle sessioni.

Ruoli previsti:

- Owner
- Admin
- Editor
- Contributor
- Viewer

La gestione dei permessi deve seguire il principio deny-by-default.

Il backend deve essere sempre autoritativo.

Non affidare mai la sicurezza ai controlli frontend.

Implementa:

- Session lifecycle.
- Session revocation.
- Protezione delle sessioni.
- Autorizzazione per risorsa.
- Isolamento tra universi.
- Gestione sicura degli inviti.
- Scadenza e utilizzo singolo dei token.
- Validazione degli upload.
- Protezione da path traversal.
- Protezione da stored XSS.
- Protezione CSRF se si utilizzano cookie.
- Validazione degli input.
- Rate limiting per le operazioni sensibili, ove previsto.
- Logging di sicurezza senza esporre segreti.

Esegui test specifici per:

1. Cross-universe IDOR.
2. API non autenticata.
3. Revoca sessioni.
4. Privilege escalation.
5. Modifiche non autorizzate da Viewer.
6. Accesso a room realtime non autorizzate.
7. Revoca dei permessi durante una sessione.
8. Upload malevoli.
9. Stored XSS.
10. CSRF, se applicabile.
11. Riutilizzo e scadenza degli inviti.
12. Leakage tramite ricerca e grafi.

# 12. DISTRIBUZIONE FINALE

La consegna deve essere progettata per Windows 10/11 con Docker Desktop.

Il progetto deve poter essere estratto nella cartella:

K:\WORLDWEAVE_M0

Deve essere presente uno script:

Avvia-WORLDWEAVE.ps1

Questo script deve:

1. Verificare la presenza di Docker.
2. Verificare che Docker Desktop sia operativo.
3. Controllare la configurazione.
4. Preparare le variabili d'ambiente se mancanti.
5. Avviare i container.
6. Attendere che i servizi siano pronti.
7. Verificare gli health check.
8. Aprire il browser all'indirizzo locale dell'applicazione.

Prevedi anche:

- Ferma-WORLDWEAVE.ps1
- Backup-WORLDWEAVE.ps1
- Ripristina-WORLDWEAVE.ps1

Non cancellare volumi o dati durante l'arresto normale.

Non includere password, chiavi o segreti reali nell'archivio.

Il sistema deve funzionare anche senza account Replit, senza dipendere dai servizi cloud della piattaforma.
